# Versioning Policy

## One source of truth

The root `VERSION` file is the sole source of truth for the application release version. It must contain exactly one semantic version in `MAJOR.MINOR.PATCH` form. The PHP bootstrap validates this value; application UI and status output must consume the derived configuration/constants rather than hard-coding a release number in templates or scripts.

Do not change the version merely to make a build look newer. Update it as part of a deliberate release commit and keep the changelog and release notes consistent with verified changes.

## Application version versus package-format version

These identifiers are intentionally different:

- **Application release version:** the semantic version in `VERSION`.
- **Server package format:** `SECURE-PKG-V14` / `.spkg14`, a serialized cryptographic format identifier.
- **Browser compatibility format:** `SECURE-BROWSER-V13` / `.spk13`, a separate legacy browser format.
- **Git tags:** immutable repository references created by the maintainer for a release; changing `VERSION` does not create a tag.

Format identifiers, magic values, extensions, fixtures, and compatibility checks must not be renamed or silently upgraded as part of routine application versioning. A package-format change requires a separate design, migration plan, and compatibility tests.

## Legacy development generations

The old V1–V14 development labels are historical identifiers, not a sequence of official semantic releases. Keep historical change explanations in Markdown and do not rewrite old commits or create an MVP-completion tag during cleanup. The maintainer will create that tag manually when ready.

Superseded source snapshots and bundled copies should not remain in the active repository tree. Preserve relevant Markdown change reports and migration notes; do not retain obsolete source bundles solely for archival purposes.

## Semantic Versioning

When the maintainer declares the first official release ready:

- **MAJOR:** incompatible application/API behavior or an intentionally incompatible package-format change.
- **MINOR:** backwards-compatible functionality.
- **PATCH:** backwards-compatible bug fixes and security fixes that do not change the compatibility contract.

A version bump must never imply an independent security audit or certification that has not occurred.

## Release checklist

1. Update `VERSION`.
2. Update `CHANGELOG.md` and release notes with verified changes.
3. Ensure `composer.lock` was generated by Composer in a supported development environment.
4. Run CI, dependency audit, self-check, source audit, and full security tests.
5. Verify server package round-trips, recovery-key restoration, tamper rejection, and no-overwrite restore behavior.
6. Verify the browser compatibility format independently.
7. Build and verify the release artifact and checksum.
8. Confirm no secrets, generated storage, temporary data, or obsolete source bundles are included.
9. Publish only after required checks pass and limitations are stated accurately.
